# 앱 발전 방향 (로드맵 메모)

출시 이후 방향에 대한 아이디어 메모. 아직 설계가 확정되지 않은 단계이며,
구현에 들어갈 때 별도 설계 문서(openspec)로 구체화한다. 당장의 미룬 작업은
`docs/implementation-todo.md`, 출시 게이트는 `docs/pre-release-checklist.md`를 본다.

(2026-10-15 작성, 같은 날 1~4차 결정 반영)

## 한 줄 요약

혼자 쓰는 신앙 기록장에서, **기록에서 뽑아낸 기도제목·독후감·간증을 비공개
그룹과 잠깐 나누는 공간**으로 확장한다. 나눔은 기한이 지나면 서버에서
사라지고, 남기고 싶은 사람만 자기 iCloud에 스크랩한다.

## 대상: 유료 구독 회원 전용

아래 그룹·공유 기능은 전부 구독 회원에게만 연다. 기존 개인 기록 기능은 그대로
무료로 둔다(별도로 결정하지 않는 한).

| 지역 | 월 구독료 |
| --- | --- |
| 미국 | $2 |
| 한국 | ₩2,000 |

- **결제: StoreKit 자동 갱신 구독(월간).** App Store Connect의 지역별 가격
  단계에서 미국 $2(실제 단계는 $1.99일 수 있음)·한국 ₩2,000에 해당하는 단계를
  고른다.

- **비구독자가 초대 링크를 받으면 구독해야만 그룹에 들어올 수 있다.**
- **구독이 만료되면** 그 사람은 그룹에서 빠지고, 그 사람이 그룹에 올린 내용도
  삭제된다. 스크랩해둔 내용은 개인 iCloud(기록장)에 있으므로 그대로 남는다.

## 기능

### 1. 비공개(Private) 신앙 그룹

- 신앙생활 정보를 나누는 SNS형 그룹. 중심 콘텐츠는 **기도(기도제목)**, 그리고
  **간증**과 **독후감**.
- 그룹은 전부 **private** — 초대받은 사람만 보고 쓴다. 공개 피드나 검색 노출은
  없다.
- **그룹 크기 제한 없음.**
- **관리자 = 그룹을 만든 사람.** 관리자 권한은 초대, 강퇴, 글·댓글 삭제.
- **관리자가 탈퇴하면** 남은 멤버들의 **위임 투표**로 다음 관리자를 정한다.
  - 후보·투표권: **그룹 멤버 전원**.
  - 투표 기간: **3일**.
  - 동률이면 **동률인 사람끼리 재투표(1일)**, 재투표도 동률이면 **랜덤으로 선정**.
  - **투표 중에는 관리자 공석** — 초대·강퇴·삭제를 아무도 할 수 없다.
  - **아무도 투표하지 않으면 그룹이 삭제된다**고 멤버들에게 알리고, **1주일
    유예 기간** 뒤 그룹을 삭제한다. 유예 기간에 스크랩할 수 있고, 스크랩해둔
    내용은 개인 iCloud에 남는다.
- **초대는 링크 또는 QR 코드.**
  - 초대 링크마다 **받을 수 있는 최대 인원**을 관리자가 정한다.
  - 초대 링크는 만든 지 **3일이 지나면 만료**된다.
- **강퇴된 사람이 올린 글·댓글은 남긴다.** 다만
  - 관리자는 삭제할 수 있고,
  - 다른 멤버는 각자 자기 화면에서 **숨김**할 수 있다 — **글 단위**(이 글만)와
    **사람 단위**(이 사람 글·댓글 전부) 둘 다.
  - 어차피 공개 기간이 지나면 사라진다.

### 1-1. 그룹 회원가입

- **무료 사용자는 회원가입이 필요 없다.** 지금처럼 Apple 로그인만으로 기록장을
  쓴다.
- **유료로 전환(구독)할 때 그룹 기능용 회원가입**을 하게 한다. 가입 때 받는
  정보는 **이름(그룹에서 보일 표시 이름)과 프로필(사진)** 정도로 최소화한다.
  프로필 사진도 그룹 사진과 같은 기준으로 압축하고 위치 정보를 지운다.
- 지금 앱은 Apple 로그인에서 이름을 받지 않고, 이메일도 기기 Keychain에만 두며
  CloudKit에 올리지 않는다(`docs/privacy.md`). 그룹 프로필은 자체 백엔드에
  저장되므로 이 경계도 착수 때 함께 고친다(구독자에 한해).

### 2. 공유 카드 자동 생성 + "올릴까요?" 추천 (공통 흐름)

세 종류 모두 같은 방식으로 동작한다.

1. 사용자가 평소처럼 기록을 쓴다.
2. 앱이 기록에서 나눌 만한 내용을 추출해 **사람들에게 공유하기 쉬운 형식(카드)**
   으로 다듬는다.
3. 앱이 주인에게 "이 내용을 그룹에 올릴까요?"라고 **물어본다**. 주인이 승인해야만
   올라간다 — 자동 게시는 없다.

| 카드 종류 | 추출 원천 |
| --- | --- |
| 기도제목 | 일기, 기도노트 |
| 독후감 | 독서노트(독후감) |
| 간증 | 일기, 기도제목 |

추출 방식은 아래 "요약·추출: Apple 온디바이스 모델" 참고.

**1단계 (서버 없음, 설계 검토 중):** 그룹·백엔드보다 먼저, 기록 → 카드 → 시스템 공유
시트(카카오톡, 메시지 등)로 온디바이스 추출과 카드 편집 UX를 확인한다. 앱은 아무것도
올리지 않는다. 설계: `openspec/changes/add-share-card-phase1/`.

### 3. 공개 기간과 자동 소멸

나눔은 영구 보관물이 아니라 **기한이 있는 대화**다. 기간이 끝나면 **서버에서
삭제**된다.

| 카드 종류 | 공개 기간 |
| --- | --- |
| 기도제목 (데드라인 있음) | 데드라인 + **3일** (데드라인 뒤에도 함께 이야기할 수 있도록) |
| 기도제목 (데드라인 없음) | 기본 **1주일**. 올릴 때 기간을 직접 정할 수도 있다 |
| 독후감 | **1주일**. 그룹 사람이 **"토론 연장"**을 누를 때마다 **1주일씩** 연장, **횟수 제한 없음** |
| 간증 | **1주일** |

- **원작성자는 기한 전에 언제든 직접 내릴 수 있다.** 내려도 다른 사람이 이미
  해둔 스크랩본은 건드리지 않는다.

### 4. 스크랩 (개인 iCloud에 보관)

- 사라지기 전에 원하는 사람은 **스크랩**해서 자기 개인 iCloud(자기 기록장)에
  저장할 수 있다.
- 스크랩은 기도노트·독서노트 같은 기존 종류가 아니라 **별도 "스크랩" 종류**로
  들어간다.
- 기록장에 **스크랩 폴더**를 만들고, 그 안에 **그룹별 폴더**로 나눠 저장한다.
- **카드에 있던 데이터를 전부 가져온다** (원작성자 이름, 본문, 카드 종류, 올린
  날짜, 데드라인 등).
- 스크랩본은 각자의 private 저장소에 남고, 그룹 서버의 원본은 기한대로(또는
  원작성자가 내리거나 구독이 만료되면) 사라진다. 원본이 사라져도 스크랩본은
  그대로다.

### 5. 댓글·반응

- 그룹 글에 **자유 형식 텍스트 댓글**을 단다.
- 텍스트 말고도 **마음을 표현할 수 있는 채널을 여러 개** 둔다. 처음 버전은
  **텍스트, 이미지(사진), 이모지** 세 가지로 시작한다.
  - **사진**을 올릴 수 있다. 단 **고화질 원본은 올라가지 않고 압축해서**
    올라간다.
  - **이모지**는 시스템 이모지를 그대로 쓴다.
  - **자기만의 이모티콘**(직접 만든 이모티콘)은 나중에 따로 설계한다.
- **사진도 글과 함께 기한이 지나면 서버에서 삭제**된다. 스크랩하면 사진도 함께
  개인 iCloud에 저장된다.

#### 사진 압축 기준 (제안)

휴대폰 화면에서 보기에 충분하면서 서버 저장·전송 비용을 작게 유지하는 선.

| 항목 | 기준 |
| --- | --- |
| 해상도 | 긴 변 **1600px**로 축소 (원본이 더 작으면 그대로) |
| 형식·품질 | **JPEG 품질 0.7** (호환성 우선. HEIC는 크기가 더 작지만 비 Apple 환경 대비 보류) |
| 용량 | 장당 **최대 500KB**. 넘으면 품질을 단계적으로 낮춰 다시 압축 |
| 썸네일 | 목록용으로 긴 변 **400px** 별도 생성 |
| 메타데이터 | **EXIF·GPS 위치 정보 제거** (사진으로 집 위치 등이 새지 않도록) |
| 개수 | 글·댓글 하나에 **최대 4장** |

압축은 기기에서 하고, 압축된 결과만 서버로 보낸다.

### 6. 알림

- **새 글**: 내가 속한 그룹에 글이 올라오면 push notification을 보낸다.
- **댓글**: 댓글이 달려도 **바로 알리지 않는다.** 대신
  - 자기 전에 **Daily Report**로 그룹 업데이트(댓글 등)를 묶어서 알려주고
    (기본 **밤 10시**, 설정에서 시각 변경 가능),
  - 앱을 열면 그때 그동안의 업데이트를 보여준다.

## 기술 방향

### 그룹 SNS 서버: 자체 백엔드 (결정)

- 그룹·글·댓글·반응(이모지·압축 사진)·초대 링크·공개 기간·관리자 투표는
  **자체 백엔드**가 맡는다. 기한 삭제, 토론 연장, 초대 링크 만료, 구독 만료 시
  콘텐츠 삭제, 새 글 push(APNs), Daily Report 발송을 서버에서 처리한다.
- 개인 기록장은 지금처럼 로컬 + 사용자 본인의 CloudKit private DB에 남는다.
  서버로 가는 것은 **주인이 승인한 공유 카드와 그룹 활동(댓글·반응 등)뿐**이고,
  일기 원문은 올리지 않는다.
- 스크랩본은 서버가 아니라 각자의 CloudKit private DB(스크랩 폴더)에 저장된다.
  새 "스크랩" 종류와 폴더 구조를 canonical 모델에 추가하게 되면
  `docs/known-issues.md`의 CloudKit 스키마 드리프트 절차를 따라야 한다.
- 착수할 때 `docs/privacy.md`("자체 기록 서버를 사용하지 않는다")와 App Store
  개인정보 라벨을 함께 고쳐야 한다.

#### Apple CloudKit으로 서버 없이 할 수는 없나? (검토 결과: 자체 백엔드 유지)

CloudKit은 개발자에게 사실상 무료다. private DB는 사용자 본인의 iCloud 용량을
쓰고, public DB는 앱 활성 사용자 수에 비례해 무료 한도가 커진다(정확한 표는
Apple이 공개하지 않으며, 내 컨테이너의 실제 한도는 CloudKit Console의 Usage
화면에서 확인). 저장 용량·비용만 보면 충분하다. 하지만 요구사항과 맞지 않는
부분이 많다.

| 요구사항 | CloudKit public DB | CloudKit 공유(CKShare) |
| --- | --- | --- |
| 그룹별로 진짜 비공개 | 어렵다 — 권한이 레코드 타입 단위라, 앱 사용자 누구나 다른 그룹 글을 조회할 수 있는 구조 | 된다 |
| 그룹 크기 제한 없음 | 된다 | **안 된다** — 공유당 참가자 보통 최대 100명 |
| 관리자 탈퇴 → 위임 | 된다(데이터 위치 무관) | **어렵다** — 데이터가 만든 사람의 iCloud에 있고 소유권 이전이 없다 |
| 기한 지나면 자동 삭제, 토론 연장 | 서버 코드가 없어 누군가의 기기가 앱을 열어 지워야 한다 | 같음 |
| 구독자만 가입·구독 만료 시 삭제 | 서버에서 구독을 검증할 수 없어 앱 쪽에서만 막게 된다(우회 가능) | 같음 |
| 초대 링크 인원 제한·3일 만료 | 직접 구현해야 하고 강제할 곳이 없다 | 링크 공유는 되지만 인원·만료 제한은 없다 |
| 새 글 push | 된다 (CloudKit subscription) | 된다 |
| 밤 10시 Daily Report | 서버 스케줄러가 없어 기기 로컬 알림으로 흉내만 가능 | 같음 |

→ 스크랩·개인 기록은 지금처럼 CloudKit private DB(무료)에 두고, 그룹 SNS는
자체 백엔드로 간다. 그룹 데이터는 기한이 지나면 지워지고 사진도 압축하므로
서버 저장량은 작게 유지된다.

### 요약·추출: Apple 온디바이스 모델 (검토 중)

Apple이 직접 제공하는 API가 있다 — **Foundation Models 프레임워크**(iOS 26 /
macOS 26부터). Apple Intelligence의 온디바이스 언어 모델을 앱에서 직접 부른다.
로컬 Xcode 26.2 SDK에 `FoundationModels.framework`가 들어 있는 것도 확인함.

- **잘 맞는 점**
  - 기기 안에서 돌아서 **일기 원문이 기기 밖으로 나가지 않는다** — 로컬 우선
    원칙과 맞고, 서버 LLM 비용도 없다.
  - **Guided generation**(`@Generable` 구조체)으로 "기도제목 목록 + 데드라인"
    같은 구조화된 결과를 바로 받을 수 있어, 카드 추출에 잘 맞는다.
  - Apple Intelligence가 지원하는 언어에서 동작하며, 한국어도 지원 언어에 들어
    있다.
- **제약**
  - **iOS 26 / macOS 26 이상 + Apple Intelligence 지원 기기**(iPhone 15 Pro 이후,
    M1 이상 Mac 등)에서, 사용자가 Apple Intelligence를 켰을 때만 쓸 수 있다.
    현재 앱 최소 지원은 iOS 17 / macOS 14라 `#available` 분기와
    `SystemLanguageModel.default.availability` 확인이 필요하다.
  - 작은(약 3B급) 모델이고 컨텍스트 창이 작다(약 4K 토큰). 긴 일기는 나눠서
    처리해야 하고, 추론·요약 품질은 큰 서버 모델보다 낮다. 한국어 신앙 글에서의
    실제 품질은 직접 시험해봐야 안다.
- **지원 안 되는 기기에서는?** 후보: (a) 추출 추천 없이 사용자가 직접 카드 작성,
  (b) 서버 LLM으로 대체(이 경우 일기 원문이 나가므로 명시적 동의 필요). 결정 전.
- 이후 OS 버전에서 모델·API가 바뀌었을 수 있으니 착수 시점에 최신 문서를 다시
  확인한다.

#### 1차 성능 테스트 (2026-10-15, M4 Mac · macOS 26.5)

테스트용으로 지어낸 한국어 기록 8개(데드라인 있는 일기, 기도노트, 기도 내용 없는
일기, 간증 일기, 독서노트, 한영 혼용 일기, 제3자 민감 사정 일기, 약 2,400자 긴
일기)로 기도제목 추출·간증 카드·독후감 카드를 시험했다. 실제 기록은 쓰지 않았다.
모델 사용 가능, 한국어 지원 확인.

| 항목 | 결과 |
| --- | --- |
| 속도 | 호출당 약 **1.2~4초** (첫 호출만 약 6.5초, 모델 로딩). iPhone 속도는 미측정 |
| 명확한 기도제목 + 날짜 | **좋음**. "다음 주 화요일(10월 20일)", "11월 3일" → 정확한 날짜, 3번 반복해도 같은 결과 |
| 상대 날짜 | **약함**. "다음 달 12일" → 12월, "다음 달(11월) 21일" → 다음 해 1월 등 오류. 작성일 기준 달력 힌트(이번 달 말, 다음 달이 몇 월인지)를 코드가 계산해 넣어주자 맞게 나옴 |
| 기도제목이 없는 글 | **약함**. 야근 일기에서 "건강 관리" 같은 없는 기도제목을 지어냄. 짧은 예시(few-shot)로 예/아니오만 먼저 묻자 바로잡힘 |
| 목록 누락 | 기도노트 5개 항목 중 2~3개만 뽑음 |
| 간증 여부 판단 | **약함**. 거의 모든 글을 간증이라고 판단. 예/아니오 분류로 바꾸자 7개 중 5개 맞힘 |
| 간증 카드 문장 | 실제 간증 글에서는 **좋음**: 사실(반년 구직, 출판사 계약직, 정규직 제안)을 살린 4문장 |
| 독후감 카드 | 책 제목·저자·인용문은 **정확**. 깨달음·토론 질문은 구조화 출력에서는 본문을 그대로 베꼈고, 자유 텍스트로 따로 물으면 **쓸 만함** |
| 제3자 이름 | 지시해도 "민지", "J" 같은 이름을 그대로 둠. 다만 "다른 사람 사정 포함" 표시는 엄마·동생·친구 사례를 대부분 맞게 잡음 |
| 안전 필터 | 평범한 야근 일기가 `guardrailViolation`으로 막힌 오탐 1건. `permissiveContentTransformations` 옵션으로 해결 |
| 긴 일기 | 약 2,400자 일기 끝부분의 기도제목도 찾아냄 (컨텍스트 초과 없음) |

**결론: 쓸 수 있다. 단 "주인이 고쳐서 올리는 초안" 용도로.** 이미 정한 "올릴까요?"
승인 흐름과 잘 맞는다. 구현할 때 지킬 것:

1. **두 단계로 나눈다.** 먼저 짧은 예시를 넣은 예/아니오 분류("기도제목이
   있나?", "간증인가?")로 추천 여부를 정하고, yes일 때만 카드를 만든다.
2. **문장은 자유 텍스트, 짧은 값만 구조화.** 제목·저자·인용문·날짜 표현처럼
   짧은 값은 `@Generable`로, 공유 문장·간증 본문·깨달음·토론 질문은 일반
   텍스트 응답으로 따로 받는다. `@Guide` 설명이 길면 모델이 설명 문장을 결과에
   그대로 베껴 넣는 현상이 있었다 — 설명은 짧게.
3. **날짜는 코드가 책임진다.** 모델은 본문의 날짜 표현만 뽑고, 실제 날짜는
   작성일 기준 달력 힌트를 넣어 계산하게 하거나 코드에서 해석한다. 카드에서
   주인이 날짜를 확인·수정할 수 있어야 한다(데드라인이 공개 기간을 정하므로).
4. **제3자 정보는 UI로 막는다.** 모델이 이름을 지우지 못하므로, "다른 사람 사정
   포함" 표시가 켜진 카드는 올리기 전에 경고하고 수정하게 한다.
5. **안전 필터 오탐 대비.** `permissiveContentTransformations`를 쓰고, 그래도
   `guardrailViolation`이 나면 조용히 추천을 건너뛴다(오류를 보여주지 않음).

#### 평가 세트 `ShareCardEval` (2026-10-15, M4 Mac · macOS 26.5)

위 1차 테스트를 다시 돌릴 수 있는 평가 세트로 만들었다 — `swift run ShareCardEval`
(실행 방법은 `docs/development.md` "공유 카드 추출 평가"). 지어낸 기록 23개(데드라인
있는 기록, 상대 날짜 — 다음 달 N일·이번 달 말·다음 주/이번 주 X요일·내일/모레·해
넘김, 기도 내용 없는 기록, 간증 vs 앞으로의 기도, 한영 혼용, 제3자 사정, 약 2,300~
2,400자 긴 기록, 독서노트 2개)에 정답 라벨을 붙이고, 위 결론 1~5대로 만든
파이프라인을 돌려 기록별 통과/실패와 지연을 낸다. 독서노트는 책 제목·저자·인용문만
채점하고, 카드 문장은 채점하지 않는다(눈으로 본다).

| 프롬프트 | 점수 | 기록 전체 통과 | 기도제목 여부 | 간증 여부 | 제3자 사정 | 데드라인 | 책 3항목 | 지연 (중앙값 / p90 / 최대) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-10-15.1 | 63/85 (74.1%) | 5/23 | 15/21 | 21/21 | 17/21 | 3/15 | 6/6 | 0.5s / 3.2s / 54.1s |
| 2026-10-15.2 | **76/85 (89.4%)** | **16/23** | 20/21 | 20/21 | 16/21 | **13/15** | 6/6 | 0.7s / 4.3s / 16.7s |

전체 실행은 카드 문장 포함 모델 호출 약 100회, 약 3분. guardrail 건너뜀은 두 번 모두
0회.

- **.1 → .2에서 바꾼 것과 효과**
  - 기도제목 분류가 .1에서는 **모든 기록에 "예"**(기도 없는 6개 전부 오답)였다.
    "하나님께 구하는 기도 문장('~하기를 기도한다', '~하게 해주세요')이 있나?"처럼
    표면 단서로 묻고, 기록 **뒤에** 질문을 한 번 더 붙이고, "아니오" 예시(할 일 목록
    등)를 늘리자 20/21.
  - 데드라인이 3/15였던 주원인은 날짜 필드가 필수 문자열이라 모델이 **모든 항목에
    작성일이나 "오늘"을 채워 넣은 것**. `datePhrase`/`date`를 optional로 바꾸고,
    "작성일 이후 날짜만 데드라인"을 코드 규칙으로 두자 13/15.
  - 모델이 직접 계산한 날짜만 쓰면 .2에서도 8/15. 모델이 뽑은 날짜 **표현**을 코드가
    해석(`DatePhraseResolver`)하는 쪽이 확실히 낫다 → 결론 3 확인. 모델이 "next
    Friday"를 "다음 금요일"로 바꿔 적는 경우도 있어 해석 규칙에 넣었다.
  - 응답 토큰 상한(분류 8, 나머지 600)을 두었다. .1에서 같은 항목을 반복하다 컨텍스트
    (4,096 토큰)를 넘기며 54초 걸린 호출이, .2에서는 상한에서 끊겨 오류로 끝난다
    (간증 기록에서 1건).
- **아직 약한 곳 (.2 기준)**
  - **제3자 사정 과잉 표시**: 지도교수님·팀원·교회 식구가 등장만 해도 "예"(5건 오답).
    UI 경고용이라 과잉 쪽이 덜 위험하지만, 너무 잦으면 경고가 무시된다.
  - **간증 + 기도가 섞인 글**: 간증에 새 기도제목이 붙은 기록을 간증 아님으로 판단.
    순수 간증 글은 기도제목 있음으로 잘못 판단하고, 이어지는 추출에서 같은 항목을
    반복하다 실패했다.
  - **한 기록 안의 두 데드라인**: "next Friday" 데모와 "Oct 30" 계약 연장을 한 항목으로
    합쳐 하나를 놓침.
  - **기도 카드 문장**: 본문을 거의 그대로 옮기거나("엄마 수술" 기록), 지시문의
    "가족, 친구, 동료"를 문장에 그대로 넣는 경우가 있었다. 제3자 이름(민지, J)은 지시해도
    두 번 모두 카드에 남았다 → 결론 4(UI 경고) 그대로 유지.
  - 영어 책 독후감의 토론 질문이 본문 문장 복사("소그룹에서 같이 이야기해 보고 싶다")로
    나옴.

다음 단계: iPhone 실기기(가능하면 iPhone 15 Pro)에서 속도·발열 측정, 위 약한 곳을
겨냥해 프롬프트 개선 후 같은 평가 세트로 비교, 기록 늘리기(특히 간증+기도 혼합, 제3자가
등장만 하는 기록).
